## 1. WHAT to think about — five difficult decisions

Your task is **not** to reword Agent A's handover. Investigate:

1. **Who is wrong about what?** Your own frozen Stage 1 model might be wrong. Agent A might have a better tested design. Both might have overlooked a consumer, failure path or Owner correction. Evaluate without loyalty to either plan.
2. **What physically works?** For each Owner-required transition, inspect an exact live source function, downstream caller, test/golden and actual provider/UI result. A PR description, pre-existing check at an older SHA, or separate green components is not an end-to-end proof.
3. **What is still the smallest essential product?** Determine which High-ROI requirements Agent A actually completed; which must be verified first; which critical end-to-end gap remains; which tempting optimization can remain parked. Do not turn every Runner hypothesis into new work.
4. **What is authorized?** Distinguish original Owner decisions, authorized graph/claim/weights, Agent A's preferences, your proposed revisions, reviewer qualification and exclusive GitHub writer rights. A new agent is not a new responsibility.
5. **What could go wrong if you act now?** Identify stale candidate/source/fixture, in-flight commits, late tool calls, changed configuration, unrun hosted CI, ambiguous original XML pairing, a protected source area or another active writer. An honest HOLD is a useful engineering result.

## 2. HOW to think — source-first reconciliation procedure

**Step A — Reopen Stage 1 verbatim.** Verify the immutable Stage 1 file and digest; read your actual Q1/Q2/Q3, original alternatives, assumptions and ROI register. Do not rewrite the Stage 1 text to make your ideas appear accurate.

**Step B — Read Agent A's *reality* without promoting its claims.** Ask for: original actual task start or UNKNOWN; exact HEAD/branch/PR; changed files/functions and consumers; initial plan/revisions/Owner decisions; tests at precise tested SHA with exits/goldens; known bugs/failed designs, parked Medium work; pending GitHub calls, lease and final proposal. Treat the packet as \`AGENT_CLAIM\` until independently checked. In a crash/no-handover case explicitly mark \`HANDOVER_MODE=INTERRUPTED_NO_PACKET\`.

**Step C — Independently inspect *current* authority and source.** Read approved Owner requirement and graph/issue changes, current candidate HEAD and source, actual downstream import/call graph, committed fixture hashes, CI job steps, source-qualified TASK_EVIDENCE, parent/child/PR publication and actual browser/download if required. Keep these separate:

- \`SOURCE_BASELINE\`: what Stage 1 was allowed to inspect.
- \`AGENT_A_TRUE_START\`: actual original task-start SHA (may remain UNKNOWN).
- \`CURRENT_CANDIDATE\`: latest exact source HEAD observed *now*.
- \`EVIDENCE_TESTED_HEAD\`: exact SHA a test actually executed.
- \`PUBLISHED_PROVIDER_STATE\`: observed issue/PR/index source and timestamp.

If they differ, explain which proof must be requalified. Do not silently promote older GREEN to newer HEAD.

**Step D — Trace each seam in Owner's full user outcome.** For every essential chain link, identify the producing module/function, consuming module/function, the same data/graph/claim basis, actual provider/UI readback and an independent falsifier. For a V3.5 case: Owner → parent → child/decomposition → task material/evidence → sole DELP projector → status/title/PR → governed index → handover. For LFJ/data conversion: source/Worker/IDB → consumer semantics → original XML matching → both CSVs → served browser. Record \`ABSENT\` or \`UNKNOWN\` instead of joining gaps with prose.

**Step E — Reconcile designs, including *your* errors.** For each material Stage 1 belief or Agent A decision, ask:
- What exact evidence supports it? Against which SHA and inputs?
- What contradiction or negative counterexample could falsify it?
- Does Agent A's implementation preserve more semantics / have stronger authentic tests than my plan?
- Did both designs ignore a user-visible outcome or failure mode?
- Is a proposed new requirement already inside Owner scope, or does it need a decision?

Use one disposition: \`ACCEPT_STAGE1\`, \`ACCEPT_AGENT_A\`, \`REVISE_BOTH\`, \`VERIFICATION_FIRST\`, \`OUTDATED\`, \`PARK_MEDIUM\`, \`REJECT_OUT_OF_SCOPE\`, \`OWNER_DECISION_REQUIRED\`, or \`UNKNOWN\`. State a short, evidence-based explanation; no private reasoning transcript.

**Step F — Construct the next credible plan.** First preserve source-verified existing High-ROI work (avoid reimplementation). Second repair missing critical product chain edges, ordered by dependency. Third park Medium-ROI improvements with estimated cost and revisit condition. Decline low-value distractions. Produce a *copy-ready* revised implementation plan / \`PLAN_UPDATE\` for the existing governed responsibility; do not create a duplicate leaf because Agent B arrived.

**Step G — Separate plan completeness from execution custody.** A read-only Stage 2 may produce a useful plan without any source-write rights. To actually code, a separate controller must prove Agent A stopped or was technically fenced, reconcile UNKNOWN writes, confirm new exclusive B epoch and scoped permissions, then re-read provider HEAD and approved graph. If that is not demonstrated, return HOLD with exact missing facts.

## 5. Verify positive *and* negative acceptance

Use problem-relevant oracles, not generic "all tests pass" assertions:

- **Semantic positive:** original authentic source, correctly paired positive target, original consumer semantics and full output/derived provider state.
- **Semantic negative:** no-match, ambiguity, duplicate identity, altered alias/configuration and invalid input must be distinguishable from success.
- **Currentness:** candidate/head, golden bytes, graph/spec generation or consumer dependency change must invalidate stale proof.
- **Failure/replay:** crash, cancellation, ambiguous push, queued tool calls or late previous actor cannot silently mutate current work.
- **Real integration:** actual parent/child/PR/index/handover or served Chromium Build/download, not independently green isolated pieces.
- **Authorization:** unverifiable Owner comment, copied predecessor claim, artificial P/E, other responsibility scope and dual executor are rejects.

For each named test, identify \`RUN_AT_SHA\`, command/browser action, input/golden hash, positive/negative expected behavior, actual observed output and independent result. If any is missing, state \`NOT_RUN\` or \`NOT_VERIFIED\`, not PASS.
